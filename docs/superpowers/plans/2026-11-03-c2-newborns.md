## Design and alternatives

Use the existing `BatchEvaluator` pool for both independent scoring and independent newborn rows. Python keeps one unique-name operation followed by one original NumPy normal request per newborn, with original shape. C++ processes each prepared row in order: blueprint plus noise, constructor clip, optional legacy modifier times 50, purification, tide, clip, norm. The original NumPy legacy dot is reused once per fixed batch. Entity construction and ordered registration remain Python; each entity owns its row and fire-seed set, begins with integer zero score and no path cache.

`BatchEvaluator.newborn_affinities(blueprint, noise, legacy_titan_modifier, purity_factor, tide, max_norm)` returns a new matrix. The C ABI validates lengths/capacity before access. A new `experimental_c_newborns` runtime flag / `--experimental-c-newborns` CLI controls initial population and growth/replenishment. A manager receives an optional evaluator factory from its owning simulation so there is one lazily allocated pool and one close owner. Unsupported custom methods/containers/RNG/configurations use the existing ordered path before consuming RNG. After batch generation starts, a native failure propagates and never retries the scalar loop.

Moving RNG and naming into C++ could remove more interpreter work but risks changing Python sampling/collision and NumPy Gaussian-cache behavior; defer until this batch boundary is measured. Parallelizing dependent interactions would change sequential world semantics and deserves a separate future experiment. C++ resident world state, merged population statistics and batch global events remain next candidates after the new profile identifies their contribution.
