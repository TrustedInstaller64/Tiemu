# A4：驻留评分、生命周期筛选和有序候选索引

本轮在 `codex/single-world-a` 继续 A。冻结对照为 A3 `f2073f001af4bc3f03da6d96d5360aa9a2027e0a`（生产代码 `5714a60`）；评分单独落地于 `b98a886`，黄金裔筛选于 `b63151f`，候选索引于 `a8f09d2`，最终保守启用策略于 `06353b7`。所有项目执行、编译、测试和计时均在 GitHub 托管机器，本机没有运行项目或安装 Docker。

## 实际迁移范围

- **评分准备与工作区**：C++ World 持有两份可复用评分缓冲，收集旧缓存、补算缺失路径、保留旧缓存先于修复的顺序，并复用原批评分核和线程池。prepare/finish 以单次 token 连接；其他 World 更新使 token 失效，公开镜像变更后 live 数值必须重新同步。
- **Python 边界**：当前只导入被评分的实体，没有为了评分再同步整个世界。公开 ndarray 可以原地改值，缓存也可以被直接替换，仍逐次检查这些修改。NumPy dot/tanh 微核保留；本轮采用逐行 vecdot 和原标量 tanh，未用 GEMV、降低精度或 fast-math 换取速度。非有限/极端输入、自定义访问器和异常配置保留旧路径及错误前缀。
- **黄金裔筛选**：只传角色、boss 和分数，C++ 给出清除旧身份的位置和稳定 top-k。相同分数仍按原人口顺序，Python 保留原清除、shuffle、方面分配和赋值顺序，不导入亲和度矩阵。该实现及契约已完成，但完整适配成本尚不值得默认启用；默认仍使用原筛选，强制原生配置仅用于本轮消融和契约测试。
- **永劫候选**：独立 C++ 索引按人口位置维护有序候选池，支持更新、排除和排名查询。Python 继续调用原随机函数；轮回者兼黄金裔保留重复权重，已淘汰者仍可能被抽中后跳过。普通交互只有发生火种转移才更新双方；每次实际轮回者交互后重新验证原人口参数并重建，支持训练/LLM 回调修改第三方、成员或顺序，无法安全重建则本代回到原选择器。

默认启用驻留评分；候选索引仅在人口至少 512、且原人口中不存在当前轮回者时启用，活跃训练段使用原选择器。完整回调后重建能力保留并通过强制路径契约测试，但默认不承担其已测重建开销。生产仍为独立 C++17/C ABI，无 pybind11、Python 头依赖或私有 BLAS 符号。Python 公开实体、每个实体拥有的缓存数组和训练调度尚未全部迁走，不能把这轮称为完整 C++ 重写。

macOS 短任务波动显著：200×2 默认/四线程预算为 0.908/1.552 倍，200×12 为 0.902/0.536 倍，而该永劫路径根本不调用人类批评分池。因此这些差异不能解释为多核训练收益；连本轮未改算法的无机样本也为 0.751 倍。这里保留不利观测，不能仅由这些短样本确认温控、调度或 GC 根因，也不能宣称所有场景都已提速。云端 macOS 不是用户本机 M1 的新测速。

强制黄金裔消融没有跨场景稳定净收益。例如 Linux 的人类 1,000×6 含轮回者由默认 1.024 倍变为 0.979 倍，永劫 200×12 由 1.007 倍变为 0.968 倍；Windows 人类 10,000×3 由 1.140 倍变为 1.036 倍。个别 Mac 样本方向相反且波动很大，不据此强制默认开启。后续应先减少 Python 元数据准备成本。

## 必须保留的中间不利结果

评分单独迁移的同机结果为：Linux 三个人类场景 1.025–1.065 倍，Windows 1.029–1.081 倍，已检查摘要一致，见 [评分阶段成对证据](performance/a4-scoring-paired-d295393.json)。

第一版把原生候选索引用于所有人口，200 实体永劫反而更慢：Linux 两代/十二代耗时增加约 23%/30%，Windows 约 20%/16%，见 [未设门槛的成对证据](performance/a4-ungated-paired-a8f09d2.json)。同轮摘要全部一致，说明结果正确不等于性能合格。

仅设 512 人口门槛也不够：[人口门槛中间证据](performance/a4-population-gated-paired-2bc09b6.json)中，Linux 的 1,000×2 仍为 0.859 倍，但 1,000×12 为 1.306 倍。边界观测显示短场景存在 44 次轮回者交互后的全量重建。因此最终进一步保留活跃训练段的原选择器，仅在无 live 轮回者的较大人口段启用 C++ 索引。512 是保守工程边界，不是所有 CPU、平台和人口形态的普适交叉点。

## 后续提速途径：本轮仅讨论

不只有提高 CPU 主频。代码可以减少必须执行的工作量；同一 runner 的迁移对照已经能验证这一点。[最终边界剖析](performance/a4-profile-06353b7.json)中，人类 10,000×3 的评分约 133.1 ms，其中 C++ prepare/finish 合计约 2.46 ms。剩余时间包括检查、打包、NumPy 微核、分配、写回和观测，**不是已经测出的纯解释器占比**。

1. **合并数值预检与准备**。消除 `np.asarray(owners)` 临时整批复制及 Python/C++ 的重复扫描，并在单次调用内去重共享模型检查。原生预检必须先保证不支持的输入无副作用回退，继续观察公开数组修改和旧缓存顺序。
2. **减少跨语言调用次数**。让 C++ 一次处理更多普通交互，遇到训练/LLM 等 Python 可回调边界再交还控制。必须逐项保持 RNG 消耗、候选顺序、已淘汰对象的抽样及回调可见状态；不能简单把抽样移前或把多步训练合并。
3. **继续迁移权威状态**。减少每阶段导入 Python 镜像与逐实体写回。公开 ndarray 别名仍是主要约束，不能只检查指针是否相同，也不能让实体缓存直接引用随后会复用的整批缓冲。
4. **只并行真正独立的工作**。输入冻结后的逐实体映射、评分与数值检查可以分块，并按原顺序提交。连续交互和在线 optimizer 更新依赖前一步，不能直接丢给不同核心。当前四线程评分没有稳定整阶段收益，默认仍为一线程。
5. **先剖析再考虑训练调度迁移**。Torch 运算本来就在原生实现里，换成 C++ 调用不自动减少计算量。只有实际 Python 调度占比足够大时才值得做；采样、前向、价值网络更新、策略网络更新、Adam 和 RNG 顺序都需单独验收。

这些后续路线未作为本轮新功能实施。没有采用低精度、并行重排训练、GPU 世界计算、NUMA 绑定或新的批量实验调度；也没有实测证据把当前瓶颈认定为 IPC、缓存未命中或 NUMA 访问。
