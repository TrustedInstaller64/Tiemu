# A3：常驻世界、实体生命周期和永劫性能

本轮在 `codex/single-world-a` 继续 A，以 A2 `eca7377`（可执行代码 `26c1c26`）为基线。全部编译、项目执行、功能测试和性能测量均在 GitHub 托管 runner；用户的 Mac 只用于静态读写和 Git，没有安装 Docker。C 分支与 AMPHOREUS 未修改。

## 已迁移的边界

- 独立 C++17 World 持有连续世界列、缓存有效位、稳定实体 ID、人口顺序及可复用工作区，通过 C ABI 调用，不依赖 pybind11 或 Python 头文件。
- 普通人类交互实际复用同一 World。Python 当前公开字段在交互前完整导入，C++ 推进原有有序交互和 MT 状态，随后只写回变化实体，保持旧数组别名、替换顺序与标量类型。
- 出生的加噪后数值处理、裁剪、纯化、潮汐与归一化进入一次 C++ 批调用。命名与 NumPy normal 仍逐实体交错，保留名字碰撞和 Gaussian cache 消费顺序；legacy dot 保留原 NumPy 归约。
- 出生后的成员登记、删除和重排使用原生 `reconcile`。旧成员在 C++ 内复制到复用缓冲，只上传新行；实体 ID 单调分配，删除后不复用。关闭/加载销毁原生状态，避免旧世界残留。
- 成员更新后数值标记为过期，完整同步前拒绝数值快照与交互；独立输入的出生计算可继续。交互失败是更严格的错误状态，必须完整同步才能恢复。无效输入不能部分提交成员或消耗 ID。

这仍是逐步迁移。Python 保留公开实体镜像、部分生命周期决策、随机调用和在线模型训练；交互入口仍有 O(N) 验证/导入。没有把 Python 的 ndarray 换成逃逸的原生借用视图，也没有宣称完整世界已脱离 Python。

## 永劫变慢的原因

冻结 A1/A2 的永劫管理器、实体和网络训练实现未变。因果消融定位到 A2 的批量路径读取在初始化选举中访问每个实体的 `__dict__`：在本次固定 CPython 3.12 环境中，这会物化实例字典，拖慢后续大量属性读取的对手筛选。

[因果诊断任务](https://github.com/TrustedInstaller64/Tiemu/actions/runs/41636705659)每个场景用三组旋转进程顺序，每进程七个新世界样本。下表是组内中位数再取中位数；独立观测不混入纯计时。

| 场景 | A1 秒 | A2 秒 | 只让 A1 物化字典 秒 | A2 恢复旧路径读取 秒 |
|---|---:|---:|---:|---:|
| 永劫 200×2 | 0.031010 | 0.032781 | 0.032683 | 0.030877 |
| 永劫 200×12 | 0.044759 | 0.054269 | 0.054370 | 0.045294 |

较长场景的 selector 被调用 1095 次，观测累计耗时分别为 0.01448/0.02387/0.02357/0.01501 秒；实际训练部分约 0.0278～0.0281 秒。两种长度每个 optimizer 都执行 15 次更新，因此较长场景增加的是普通交互/筛选，不是训练步数。仅恢复分布统计或关闭 GC 不能去除差异。各消融的已检查状态、RNG 与 optimizer 更新均相同。

修复保留批量路径映射，改为普通字段读取，并在读取前拒绝 descriptor/自定义属性访问。机制测试直接检查字典没有被物化，不用不稳定的时间阈值判定通过。完整证据见 [初轮诊断](performance/a3-aeonic-initial-42b8fdf.json)与[因果消融](performance/a3-aeonic-causal-74e89b6.json)。

## 保留的不利中间结果

首版 `74e89b6` 已真正复用 C++ World，但出生后再次打包、验证和同步全部人口。在同一 Linux runner 上，人类 10,000×3 从 A2 的 0.478508 秒变为 0.801197 秒，约慢 67%；1,000×6 从 0.082710 变为 0.089850 秒。功能一致不能代替性能验收。

[首版 profile](performance/a3-profile-74e89b6.json)证明大量时间在 Python 的进化/状态准备，原生出生只占极小部分。后续改用成员 reconcile，并按 C++ 变化位/事件集合稀疏写回，消除上述多余工作。[首版同机结果](performance/a3-paired-linux-74e89b6.json)保留，不以不同 runner 的绝对耗时拼接速度倍率。

`1f3b050` 的 Linux 大人口仍从 0.442111 变为 0.608079 秒；`149442f` 改为一次结构化记录打包和批量 ID 转换后，其本轮同机对照仍从 0.592794 变为 0.670725 秒。[第二版](performance/a3-paired-linux-1f3b050.json)和[第三版](performance/a3-paired-linux-149442f.json)均保留，不能仅凭架构迁移或小人口提速宣称完成性能目标。

进一步[消融](performance/a3-human-dictionary-ablation-19c27c2.json)把字典物化放到计时前，只把 10k×3 从 0.782193 改为 0.767580 秒。这不足以支持“首次物化成本从初始化移入计时区间”是主要回退原因。后续入口修改改为核对普通方法的绑定函数/对象，使正常实体全程保持未物化字典；这与提前物化是不同实验，必须另看成对结果。真实方法替换仍回退；Python 本来忽略的 property 同名实例字段则通过新增逐次冻结循环对照验证安全接受。

macOS 的短永劫 200×2 单线程仍为 0.934×，即耗时增加约 7.1%；不能宣称所有场景提速。同一轮候选的几个线程预算配置为 0.01220～0.01592 秒，而该永劫场景不使用人类评分线程池，这种差异不能归因于并行训练。较长场景和其他平台支持修复方向，但共享 runner 的三次短样本仍不足以保证每次运行更快。无机算法本轮未改，接近 1×的正负变化也不作为优化收益。

[最终 profile](performance/a3-profile-5714a60.json)的完整性检查通过：每代实际调用原生交互，整段人类阶段使用同一个 World；普通、观测、四线程和字典消融的已检查状态/RNG 一致。10k×3 单线程观测中，评分路径 192.0 ms，入口检查 186.8 ms，进化 189.6 ms；C++ 交互仅 9.39 ms，C++ 评分约 2.17 ms。包含时间重叠，不能相加，也不能据此宣称其余全部是解释器开销。仅强制物化字典的对照比正常路径慢约 7.4%，是另一项支持保持普通属性访问的有限诊断证据。

四线程没有稳定整阶段额外收益，默认继续为 1。有限阶段一致性不等于任意长演化或跨 CPU/GPU/LLM 后端逐位一致；云端 macOS 也不是用户 M1 的新实测。性能摘要覆盖实体顺序、序列化字段、原始路径缓存、派生数值、轮回者、蓝图、席位、三网络权重、Adam 与 Python/NumPy/Torch RNG，不涵盖每个内部管理器字段。数组别名、生命周期、逐次 RNG 和标量类型由专门差分测试另行覆盖；原版回放保留现有 float64/float32 容差和严格离散断言。

后续迁移优先级由本轮 profile 和静态分析支持，以下尚未实施，也没有承诺提速倍率：

1. **World 内的评分准备和结果状态。** 当前评分路径大部分时间在 Python 逐实体旧缓存乘数、有限值检查、输入装箱与输出赋值，已有原生评分很短。迁移时必须分开“旧缓存计算乘数”和“当前亲和度重新映射”，保留非有限值修复时点与独立数组；不能因 World 持有数据就跳过公开镜像导入。
2. **同一未修改阶段内共享路径统计和选举输入。** 将缺失缓存补齐、主导路径、直方图与投票输入放在连续原生阶段，减少重复扫描、stack 和临时直方图。保留已有有效但陈旧的缓存、首次出现顺序和并列规则；仅 12 元素的 NumPy 席位排序可暂留原路径，避免重写不稳定排序引入差异。
3. **生命周期筛选与稳定排序。** 先迁移黄金裔候选过滤/排序、身份变更和存活顺序，再考虑精英统计。Python 在原位置执行原 shuffle，将结果传给 C++。同分顺序、非有限分数、名字删除语义和即使空候选也发生的 RNG 消费均须保留；不能简单用 std::sort/另一种归约替代 NumPy 阈值。
4. **永劫每代有序候选索引。** 当前每次选择重新扫描全人口；每代人口在循环尾才修改，可一次建表、交互后更新火种/泰坦标志。必须保留转生者兼黄金裔的重复权重、已死亡成员仍可能被抽中后跳过、单候选也消耗随机数，以及原人口顺序。先逐次比较实体身份与 RNG，再比较真实训练权重/Adam 状态。

提高主频可能减少当前串行路径耗时，但不是唯一办法。减少 Python 对象操作、重复扫描、装箱和边界传输，同样直接减少工作量。纯 C ABI 不直接检查 Python 方法覆盖、ndarray 所有权等对象语义；持续扩大原生阶段才有机会摊薄这类检查。数值核之外的工作尚未迁走时，盲目增加评分线程无法消除主要瓶颈。在线训练仍按原顺序每次更新，不通过合并 optimizer step 获得所谓等价提速。
